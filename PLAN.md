# Friend — виртуальный компаньон. План работ

Компаньон живёт поверх всех окон: 2D-персонаж (PixiJS) в прозрачном окне, Go-сервер
держит состояние, память и планировщик, LLM — NVIDIA NIM (OpenAI-совместимый API).

## Что уже решено (и почему)

| Вопрос | Решение | Почему так |
|---|---|---|
| Обёртка (прозрачное окно) | **Electron на этап 1**, Tauri — переезд позже | На машине нет Rust/cargo (`cargo: command not found`). Tauri без тулчейна не собрать, а Rust-сборка на слабом ноуте — это гигабайты и десятки минут. Фронтенд — обычная веб-страница, обёртка тонкая: переезд на Tauri = замена одного файла, без правок персонажа и сети. |
| Аватар | Процедурный (PixiJS Graphics), внешний спрайт — по желанию | Готовой графики нет. Рисуем программно: видно сразу, ничего не качаем. Появится арт — кладём PNG и указываем в конфиге, код не меняется. |
| Язык персонажа | Русский | Ты пишешь по-русски; язык — поле в конфиге. |
| Ключ LLM | Файл `.env` в корне + переменная окружения (`NVIDIA_API_KEY`); в конфиге — ИМЯ переменной | Требование «никаких хардкодов ключей». Но «задать переменную» на Windows — это setx с перезапуском, поэтому сервер сам читает `.env`: человек вставил строку и запустил заново. Значение не логируется никогда, среда сильнее файла. |
| Модель NIM | `openai/gpt-oss-20b` | Замерено живьём: исходная `meta/llama-3.1-8b-instruct` снята с обслуживания (410 end of life), большинство моделей каталога отвечает 404 «не для этого аккаунта». Из работающих `nemotron-3-super-120b-a12b` думает 6–20 с, `gpt-oss-20b` — 2–7 с. Лимит токенов поднят до 1024: на 300 «думающие» модели отдают пустой ответ. |
| Внешность | Пиксельная девушка нарисована кодом (сетка 40×56 + палитра + автообводка) | Готовый спрайт — чужие лицензии и чужая сетка кадров, а нужны СВОИ состояния: моргание, взгляд за курсором, разговор, эмоции, взмах рукой, поглаживание. Код рисует части по отдельности и анимирует их независимо. |
| Зависимости Go | `gorilla/websocket` (уже в кэше модулей) | В stdlib нет WS-сервера. SQLite (этап 3) добавим тогда же, когда появится память. |
| Порт и адрес | `127.0.0.1:8787`, конфиг + env | Сервер локальный: наружу ничего не торчит. |
| Запуск | `start.bat` в корне проекта | Пользователь должен запускать ОДИН файл, а не помнить порядок команд. Батник каждый раз пересобирает сервер и останавливает прошлый запуск: запущенный `.exe` Windows не даёт перезаписать, а старый сервер рядом с новым кодом — это ложные баги. |
| Кто пишет позицию | Только настоящее окно (оболочка) | В браузере позиция окна — выдуманная величина (страница считает её от размера своей панели). Открытая в браузере вкладка перезаписывала сохранённое место персонажа при каждом переподключении — персонаж «сам переезжал». |

## Этапы

**Этап 1. Каркас** (сделан)
- Go-сервер: конфиг, уровни логов, состояние на диске, WebSocket-хаб, `/healthz`.
- Веб-персонаж: PixiJS, прозрачный фон, процедурный аватар, перетаскивание мышью.
- Позиция окна сохраняется на сервере и восстанавливается при запуске.
- Обёртка Electron: прозрачное окно без рамки, always-on-top, тащится мышью.
- Запуск одним файлом (`start.bat`) и самопроверка оболочки (`--selftest`).
- Проверка: см. README, разделы «Запуск» и «Проверка оболочки без человека».

#### Что выяснилось на живом запуске (и было исправлено)

Всё найдено замером, а не взглядом в код:

1. **Перетаскивание не работало вообще.** Страница звала `friendNative.moveBy`,
   а `preload.js` отдавал метод под именем `moveWindow` — обещание отклонялось,
   и отказ нигде не печатался. Теперь набор методов проверяется самопроверкой,
   а отказ оболочки виден в консоли страницы.
2. **Окно двигалось 46 пикселей вместо 50** на пяти шагах по 10. Причина —
   масштаб дисплея 125%: окно живёт в целых пикселях, и каждый шаг округляется.
   Поэтому цель считается от начала протяжки (остаток переносится на следующий
   шаг), а в конце — выравнивание по свежему замеру.
3. **Быстрая протяжка терялась целиком:** позиция окна запрашивалась
   асинхронно при нажатии и не успевала приехать к концу движения. Теперь все
   обращения к оболочке идут одной очередью, а позиция окна узнаётся из первого
   же ответа на переезд.
4. **Мышь ловил весь прямоугольник окна** — 320×420 пикселей отнимали клики у
   рабочего стола. Теперь хватает только персонажа (проверяется тестом).
5. **Страница в браузере перезаписывала сохранённую позицию** при каждом
   переподключении — настоящий персонаж из-за этого «сам переезжал».
14. **Окно было впритык по фигуре**, поэтому облачку реплик было некуда расти, а
   меню не помещалось вообще. Теперь окно больше спрайта на постоянные поля, при
   меню расширяется вбок и возвращается обратно, а «точка отсчёта» — НЕ центр
   окна, а её ноги на экране: иначе изменение окна сдвигало её саму.
15. **«Понимание приложений» из Desktop Mate/MateEngine скопировать не с чего** —
   там реакция на музыку и события конкретных игр, а не чтение активного окна.
   Поэтому это своя задача (сделано 2026-10-22, см. раздел «Понимание экрана»).
16. **Жалобы на исчезновение есть и у них:** у Desktop Mate персонаж терялся за
   экраном после смены мониторов (лечится удалением настроек в реестре), у
   MateEngine — при посадке на свёрнутое окно и на нескольких мониторах. Вывод:
   наша память позиции с клампом и сторож кадров — не перестраховка, а
   обязательная часть.
17. **Окно раздувалось на глазах при протяжке**, а вместе с ним растягивались
   облачко реплик и поле ввода — «диалоговое окно на весь экран». Причина
   измерена отдельной пробой: `BrowserWindow.setPosition` на этой машине
   (Windows, масштаб экрана 125%) растит окно примерно на 1,3 пикселя ЗА ВЫЗОВ и
   при этом может не сдвинуть его вовсе — 60 вызовов дали 320×420 → 401×504,
   ещё 120 — 561×664. Протяжка мышью делает таких вызовов шестьдесят в секунду.
   Дополнительно выяснилось, что ЧТЕНИЕ размера из `getBounds` и возврат его в
   `setBounds` тоже растит окно (200 таких круговоротов: 320×420 → 520×620).
   Поэтому переезд идёт только через `setBounds` с ЯВНЫМ размером, который
   попросила страница; тот же `setBounds` замером подтверждён как точный
   (200 переездов — размер на месте, окно доезжает пиксель в пиксель, 353 мс на
   200 вызовов). Плюс в сторож добавлен возврат размера и проверка в
   самопроверке на 120 шагов протяжки.
18. **«Посадка у края экрана» выглядела обрезанной полосой**, а не «она
   выглядывает»: окно свешивалось за край на четверть фигуры, и видна была
   вертикальная полоса спрайта без всякого движения. Теперь окно встаёт кромкой
   ровно к краю экрана, а прячется и выходит движение спрайта внутри окна
   (`web/js/peek.js` — ритм, `web/js/main.js` — геометрия): обрезку делает сама
   картинка, поэтому она исчезает ровно по краю экрана, ничего не «утекает» на
   соседний монитор, а движение остаётся плавным — это отрисовка, а не переезд
   окна через IPC. Проверка меряет обе крайние позы числами и требует минимум
   пять разных положений за 1,2 секунды (иначе это рывок, а не выход).
19. **Протяжка не доезжала до курсора на десятки пикселей** — и это оказалось
   той же болезнью, что и рост окна: переезд на ДЕЛЬТУ оболочка считает от
   позиции, которую только что прочитала, а чтение отстаёт и округляется
   (масштаб 125%). На пяти шагах по 10 окно проезжало 46, на длинной протяжке
   терялось до 35 пикселей. Теперь цель протяжки АБСОЛЮТНАЯ ("поставь окно
   сюда"), её можно повторять сколько угодно — результат один и тот же; дельта
   осталась только на самом первом шаге, пока точка отсчёта ещё не известна.
   Проверка: сдвиг 100×48 из 100×50 и длинная протяжка 0,−2 от курсора (было
   −35). Заодно синтетические протяжки в самопроверке отключают системную мышь
   (`setIgnoreMouseEvents`) — иначе живой курсор над ползущим окном подмешивал
   свои ходы, и замер получался случайным, а не замером кода.

6. **Два запуска давали двух персонажей**, которые спорили за сохранённую
   позицию. Теперь второй экземпляр окна не открывается, а `start.bat` гасит и
   прошлое окно: иначе после правки кода оболочки старое окно продолжало бы
   работать по старому коду, а второе не открывается.
7. **Персонаж улетал с экрана и не возвращался.** В файле состояния лежало
   `-26215,320`: окно ставили туда, оно оказывалось за пределами рабочего стола,
   и достать его мышью было нельзя. Причина накопительная — координаты писались
   без проверки, что окно вообще остаётся на экране. Теперь позиция клампится в
   рабочий стол при любом переезде, а если оболочка поставила окно не туда,
   страница отправляет серверу настоящее место — память исправляется сама
   (проверяется в самопроверке: запросили `-26215,320`, окно на экране, на сервере
   правильный адрес).
8. **Окно «дрыгалось по всему экрану».** Точка отсчёта протяжки считалась от
   несуществующего места: когда окно не доезжало до цели (упиралось в край или
   его поправляла оболочка), разница копилась, и каждый следующий шаг тянул окно
   всё дальше. Теперь точка отсчёта пересчитывается от факта (тест: сдвиг ровно
   100×50 от безопасной точки).
9. **Модель из конфига оказалась снята с обслуживания** (410, end of life), а у
   аккаунта из каталога доступна лишь горстка моделей (остальные — 404). Плюс
   «думающие» модели на маленьком `max_tokens` отдают пустой ответ. Отсюда:
   смена модели по замеру, лимит 1024 и понятное сообщение про лимит вместо
   «пустой реплики».
10. **Рука отъезжала от тела.** Взмах вращался вокруг точки, которая не была
   плечом, и рука жила отдельной жизнью. Теперь контейнер стоит ровно в плече,
   амплитуда взмаха — 0,09 радиана.

**Этап 2. Диалог** (сделан)
- ✅ Личность отдельным файлом (`server/internal/persona/mira.json`, встроен в
  бинарник через `go:embed`; свой файл можно указать в конфиге и получить на
  него шаблон командой `-dump-persona`). Системный промпт собирается кодом:
  кто она, как звучать сейчас (часть суток — утро/день/вечер/ночь, время,
  язык) и запреты. Тесты — характера и частей суток.
- ✅ Клиент NIM: OpenAI-совместимый `chat/completions`, ключ читается из env в
  момент запроса (в конфиге — только имя переменной), понятные ошибки (нет
  ключа / ключ не принят / модель не найдена / сбой API), предел ответа и
  дедлайн. Тесты — на поддельном HTTP-сервере, включая стенд «ключа нет».
- ✅ История разговора (`internal/chat`): последние 20 реплик, вытеснение
  старых, копия истории наружу. Тесты — на лимит, порядок и подменяемых часах.
- ✅ Разговор (`internal/companion`): системный промпт собирается на каждую
  реплику, реплика человека попадает в историю ДО запроса, ответ — только при
  успехе (пустую реплику помнить нечего). Тесты — на сборку запроса, порядок
  истории, сбой модели и дедлайн.
- ✅ Протокол `say`/`thinking`/`reply`/`reply_error` + история в `welcome`.
  Ответ считается в отдельной горутине (иначе окно замирает на время ответа),
  очередь реплик (3) с понятным отказом вместо накопления. Тесты — на порядок
  кадров, ошибки без ключа, независимость окна от ответа и ограничение очереди.
- ✅ Окно ввода, облачко реплик, индикатор «думает» (js/chat.js). Реплика
  человека видна сразу, индикатор гасится и по таймауту (страховка от «думает
  навсегда»).
- ✅ Женский род: `gender: female` в характере и правило с примерами в промпте
  (раньше модель отвечала «я пришёл»).
- ✅ Внешность: пиксельная девушка вместо процедурного «блоба» (см. таблицу
  решений) — с эмоциями, морганием, взглядом за курсором, разговором ртом и
  взмахом рукой.
- ✅ Поглаживание по голове: 2 с быстрых движений по волосам → улыбка и
  пиксельные сердечки (js/pet.js + сердце в avatar.js).
- ✅ Сторож окна: персонаж больше не может «уехать в никуда» (см. «что
  выяснилось» ниже).
- Проверка: `go test ./...` (все пакеты), живой вопрос-ответ с настоящим ключом,
  и самопроверка оболочки `npx electron . --selftest` — 5 частей, код возврата 0.

**Этап 3. Память** (сделан 2026-10-22)
- ✅ `internal/memory` (SQLite через `modernc.org/sqlite` — чистый Go, без cgo):
  архив реплик (convo), факты (facts) с FTS5-полнотекстом, саммари (summaries)
  по одному на день. Файл `memory.db` в каталоге пользователя, WAL, наружу не
  уходит ничего.
- ✅ `запомни: …` — команда в окне ввода: факт в базу, подтверждение репликой,
  работает БЕЗ ключа модели (память локальная, модель тут не нужна).
- ✅ Подбор фактов к ответу: FTS5-поиск по последней реплике человека с
  усечением слова («отец*» → «оте*», «кот*» → «ко*») — падежи ловит, русский
  сгибается; запрос из предлогов — свежие факты. В промпт попадает подборка
  (≤5 фактов + вчерашнее саммари), а не весь архив, с прямым запретом
  пересказывать список.
- ✅ Ночное саммари: на смене части суток на ночь модель сжимает разговор
  за сутки в заметку о человеке; один раз на день (проверка по базе, не по
  памяти процесса), при <$3 реплик человека — молчит, при сбое — Warn.
- ✅ Векторный поиск не нужен: на локальной машине FTS5 с усечением слов
  делает подбор фактов без эмбеддингов и без сети. Решение принято по замеру.
- ✅ Архив реплик → восстановление истории при старте: после перезапуска
  сервера она помнит и вчерашний разговор (последние N реплик живой сессии),
  и все факты.
- Проверка (сделана): `go test ./...` зелёный (память 9 тестов, хаба 4 теста
  про «запомни:», компаньон тесты промпта с памятью); живой прогон:
  `запомни: кота зовут Барсик` → «Запомнила: кота зовут Барсик»; вопрос
  «Как зовут моего кота?» → «Твой кот – Барсик»; ПЕРЕЗАПУСК сервера (лог
  «история восстановлена из памяти, реплик=4») → новый вопрос → «Конечно,
  твоего кота зовут Барсик».

**Этап 4. Проактивность** (главное, сделан 2026-10-22)
- ✅ Понимание окна человека (focuswatch → `focus` → строка обстановки в промпте) —
  сделано 2026-10-22, см. раздел «Понимание экрана» ниже.
- ✅ Планировщик `internal/proactive` (чистая функция `Tick`, тик 30 с настраивается):
  анти-спам — не чаще одного сообщения в 25 минут, а «занят» (код/игра/офис/
  терминал) → пауза вдвое дольше; повторный намёк по тому же поводу — не раньше
  чем через 5 минут («она пыталась и не смогла» не превращается в стук).
- ✅ Триггеры (по приоритету): сон после 3:00 («иди спать», раз за ночь, разрешён
  в окно тишины) → она засыпает сама после 25 мин без мыши (раз в 2 ч, тоже в
  окно тишины) → вода/еда (из конфига, по умолчанию 3 ч) → марафон в приложении
  (2 ч в одном окне → «код не убежит, может, чай?», один раз на заход в приложение)
  → приветствие при смене части суток (утро/вечер) → мягкий намёк после 60 мин
  молчания (занятого не тревожит). Дата и погода — в списке на потом.
- ✅ Окно тишины 23:00–7:00: спит всё, кроме «иди спать» и её собственного
  засыпания.
- ✅ «Занят → реже»: пауза анти-спама удваивается по классу активного окна
  (строка обстановки для этого уже была).
- ✅ `companion.Speak(повод)`: реплика по поводу одним сообщением от неё;
  повод — служебная инструкция, в историю разговора не попадает (там только её
  реплика). Без ключа — не стреляет запросами.
- ✅ Оболочка дополнена idle-таймером человека (`GetLastInputInfo`): кадры `focus`
  несут поле `idle`; heartbeat раз в 30 с обновляет «он пропал N минут», когда окна
  не меняются. Сервер обрезает дикий idle и честно не считает «его нет», пока
  мышь не видела ни одного замера.

## Трей и автозапуск: сделано (2026-10-22)

У окна компаньона нет рамки; до этого «закрыть окно» (Alt+F4, закрытие
программой, смерть оболочки) значило расстаться с ней вместе с сервером.

- ✅ **Трей.** Оболочка ставит значок в уголок уведомлений: сначала базовое

  «показать / скрыть» — являются и уходят.
- ✅ **Закрытие окна = прятанье.** `win.on('close')` с флагом `isQuitting`:
  без выхода окно гаснет, а живёт — сервер, озвучка, фоновый слушатель не
  трогаются. Настоящий выход («Выход» из меню трея, «выход» из её меню,

  спрятано, а не закрыто.
- ✅ **Автозапуск при входе.** Галка «запускать при входе» в её меню
  (по умолчанию ВЫКЛ: без явного желания реестр не трогаем) → preload →
  `app.setLoginItemSettings({openAtLogin, args:[папка приложения]})` — штатный
  ключ `HKCU\...\Run`, без администратора; команда запуска = тот же
  electron.exe с папкой `desktop` (то же, что start.bat, без консоли).
  На Windows `getLoginItemSettings` сравнивает команду ПОЛНО — читать надо
  с теми же args, что писал (без args даёт false при включённом запуске);
  в оболочке чтение и запись используют один и тот же список args.
  Старт с включённой галкой восстанавливает ключ, если человек удалил его
  вручную; выключенный — не навязывает. Галка откатывается, если оболочка
  не смогла применить (меню не показывает то, чего нет).
- Проверка: 19-я часть самопроверки exit 0 — «трей и автозапуск — OK (иконка
  11×16, close→скрыта true, из трея видна true, openAtLogin

  окно живым и невидимым; показ из трея возвращает видимость; запись

  оставляет на чужой машине тестовую запись в автозагрузке).

## Понимание экрана: сделано (составная часть этапа 4, 2026-10-22)

Личные комментарии вместо универсальных реплик: ей нужен ТОЛЬКО заголовок и имя
процесса активного окна — этого хватает, чтобы знать «редактор кода», «браузер»,
«игра», не читая ни строчки содержимого.

Как сделано (по тому же плану, что был в этом разделе):

1. ✅ Помощник `cmd/focuswatch` (только Windows, одна команда сборки):
   `GetForegroundWindow` + имя процесса (`QueryFullProcessImageNameW`, минимальные
   права на процесс) + заголовок; печатает JSON-строку в stdout ТОЛЬКО при смене
   окна; умирает по закрытию stdin (умерла оболочка — вышел помощник).
2. ✅ Оболочка запускает помощника, читает stdout, перезапускает при смерти;
   страница пересылает смены на сервер кадром `focus` (поле `app`/`title`) и
   присылает последнее окно заново при восстановлении канала.
3. ✅ `internal/focus`: классификация (код/браузер/переписка/игра/музыка/офис/
   терминал; неизвестное — «неизвестное» с явным запретом выдумывать), трекер с
   счётом «уже 2 ч» (счёт от последней СМЕНЫ приложения, смена вкладки не
   обнуляет), строка обстановки в системном промпте (Companion.SetContext).
   Окно самой Миры (electron) и рабочий стол (explorer) в промпт не попадают.
4. ✅ `/healthz` отдаёт текущее окно; самопроверка оболочки проверяет оба факта:
   помощник выдал строки (Windows API жив) и цепочка страница→сервер дошла
   («сервер помнит Code.exe (code)»).
5. ✅ ПОВОД заговорить первой (долго одно и то же окно, полночь, вернулся после
   молчания) и окно тишины — планировщик `internal/proactive`, сделано там же,
   2026-10-22 (см. «Этап 4» выше).

Приватность соблюдена: список приложений не уходит никуда, кроме текста запроса
к модели; заголовки шлются (по ним видно «читает ТАСС»), сервер обрезает их до
160 знаков и вычищает управляющие символы.

Что выяснилось на живом прогоне:

- Помощник срабатывает на закрытие stdin как на смерть родителя — проверка
  «запустил в консоли без родителя и он молча умер за секунду» поймана именно
  так; в оболочке stdin держится открытым, всё штатно.
- Самопроверка на холодном старте (первый запуск после сборки) ловила падение
  поглаживания: прогресс не успевал набрать 2 с при прогретой системе; повторный
  прогон зелёный. Самопроверка теперь печатает прогресс поглаживания (мс),
  волочение и геометрию головы — падение видно числами, а не «похоже, сломалось».
- Порог поглаживания был настроен под синтетику, а не под человека: 2 с
  НЕПРЕРЫВНОГО движения строго по голове, обнуление на каждом выходе за
  край волос. Живой человек водил курсором по голове — реакции ноль
  (на каждом развороте ладони курсор на долю секунды съезжает с головы).
  Теперь: порог два взмаха (1,1 с), короткий вылет за край (до 350 мс)
  счёт не сбрасывает, пауза «мышь стоит» — 700 мс.

Что выяснилось на проактивном прогоне (ускоренное время):

- `go build ./...` НЕ пишет исполняемые файлы — тест прогонял старый `bin/companion.exe`
  без планировщика и ждал реплики в пустоту. Живые прогоны собираются только с `-o`.
- У NVIDIA NIM эта машина регионально заблокирована (451), поэтому проактивный
  прогон идёт на локальную модель из рабочего конфига (`fast-proactive.json`).
- Тестовый клиент на websocket не делает второй `Read` после дедлайна
  (gorilla ломает соединение) — срок ставится один на весь прогон.

Что выяснилось на живом прогоне памяти (FTS5-поиск по-русски):

- `отец*` НЕ находит «отца» — чередующаяся гласная, общий префикс только «от».
  Поэтому запрос — начало слова без двух последних знаков (минимум 2 буквы).
- В GROUP с OR (`(a* OR b*)`) запрос ломается; `bm25`/`rank` виден только
  внутри FTS-таблицы — ранжирование живёт в подзапросе `IN (…)`.
- Тот же запрос через `JOIN` на префиксных OR терял строку (замерено на живом
  движке) — форма с `IN (SELECT rowid …)` стабильна.
- `go test` ловит это на своих данных: тесты фиксировали пустые выборки до
  того, как форма запроса стала правильной.

Что выяснилось на прогоне звука (WASAPI-лупбек чистым Go):

- cgo с TDM-GCC: слинкованный PE32+ (24 секции) не запускается НИКТО — ни
  MSYS-exec («Exec format error»), ни сам Windows (WinError 193). WASAPI-
  интерфейсы — обычные vtable-вызовы, поэтому `syscall.Syscall9` по
  указателям функций покрывает их без cgo целиком.
- Chromium-захват микшера на этой машине (масштаб 125%) мёртв:
  `desktopCapturer.getSources` и getDisplayMedia с видео убивают рендерер
  («Terminating renderer for bad IPC message, reason 263»), аудио-only
  getDisplayMedia — NotSupported, mandatory `chromeMediaSource` — промис
  виснет. Единственный живой путь — помощник процессом.
- GUID'ы в заголовке TDM-GCC местами ОЛИЧЬЯ от официальных Windows SDK
  (mingw-варианты): `CoCreateInstance`/`Activate`/`GetService` сравнивают
  GUID побайтно, и «заголовочный» вариант отвечает `E_NOINTERFACE` /
  `CLASSNOTREG`. Полагаться надо на официальные значения, а vtable-слоты
  сверять с фактическим порядком методов в этом же заголовке.
- `vcall`-обёртка обязана поддерживать ноль аргументов: `Start(This)` без
  ветки case-0 возвращает E_INVALIDARG, не доходя до COM.
- Порядок обязательный: `Initialize` (c `AUDCLNT_STREAMFLAGS_LOOPBACK`,
  shared=0, периодичность 0) → `Start` → `GetService(IAudioCaptureClient)`.
- Помощник печатает строку раз в 200 мс и сам перезапускается при смене
  звукового устройства (обрыв захвата — не смерть).
- «Танцует под свой голос» оказалось багом: TTS из колонок попадал в детектор
  как громкость, и после остановки музыки её ответы по чату продлевали танец
  бесконечно (feed-тест это не ловил: там нет её голоса). Введён счётчик
  последней ВНЕШНЕЙ громкости: её речь в тишине без музыки = тишина, в
  музыкальном контексте не мешает; в feed-режиме появился переключатель
  feedSelf для этого кейса.

Что выяснилось на ходьбе по экрану (баг «ноги пропадают, когда она бегает»):

- Кадры ног (`legGrids`) — сетки РАЗМЕРОМ СО СПРАЙТОМ в абсолютных координатах
  (ноги на строках 49..55). Тело копировало их со сдвигом (6+x, 48+y): строки
  уезжали за 97-ю сетки 40×56, `set` их обрезал — и при ходьбе ноги не
  дорисовывались вообще. Копирование без смещений починило.
- Цикл шага собирался как `[A, flipX(B)]`, где B — второй кадр со своими
  смещениями: обе ноги оказывались склеены у центра, шаг не читался. Правильный
  цикл — `[A, flipX(A)]`: второй кадр есть первое зеркально.
- Пиксельная проверка кадров (`walkLegTest` — группы columns ног в строках
  50..53) поймала обе поломки до прогона: у битвых кадров групп не было вообще,
  у зеркального цикла группы второго кадра = 39 − группы первого.

## Этап 8. Кроссплатформенность (план, 2026-10-23)

Цель: Мира работает на Windows, Linux и macOS — там, где это физически
возможно, с честными ограничениями вместо обещаний. Приватность неизменна
на всех ОСях: focus — только имя процесса и заголовок окна; звук — только
RMS-число; TTS — только текст её реплики; STT/wake — полностью локально.

### Что уже кроссплатформенное (инвентарь по коду)

- Страница (`web/`): чистый JS + PixiJS — работает где угодно.
- Go-сервер: чистый Go без cgo — `modernc.org/sqlite` (SQLite без C),
  `gorilla/websocket`, stdlib. `go build` для linux/darwin не требует тулчейна.
- Пути: `os.UserConfigDir()` (`%AppData%\Friend` / `~/.config/Friend`),
  TTS-кэш, STT-модель и папка спрайтов уже идут от него.
- Помощники: `focuswatch` (`collect_windows.go` + заглушка
  `collect_other.go`) и `soundwatch` (`wasapi_windows.go` + заглушка
  `wasapi_other.go`) — сборка на любой ОСи уже проходит, фичи деградируют
  вежливо (JSON с причиной, оболочка не танцует, «понимания окна» нет).
- Electron: `workArea`, прозрачность, `skipTaskbar`, `setAlwaysOnTop`,
  Tray, `setLoginItemSettings` — API общие; масштаб экрана учитывается
  через рабочий регион, а не через win32- DPI.
- TTS/STT ищутся через `exec.LookPath("edge-tts")` / `exec.LookPath("python")`
  — путь к бинарнику, а не фиксированный `.exe`.

### Этап 8а. Linux (делаем первым)

1. `server/cmd/focuswatch/collect_linux.go` (build tag linux): X11-протокол
   чистым Go (открыть сокет `/tmp/.X11-unix/X0`, handshake, `GetProperty`
   `_NET_ACTIVE_WINDOW` → `GetGeometry`+`_NET_WM_NAME`+`_NET_WM_PID`),
   idle — MIT-SCREEN-SAVER `QueryInfo` (цикл 1 с). Схема вывода та же:
   `{"process":…,"title":…,"idle":сек}`. Wayland: заглушка с ясной причиной.
2. `server/cmd/soundwatch/level_linux.go` (build tag linux): PulseAudio
   native protocol (cookie auth → `/run/user/$UID/pulse/native`, handshake,
   `CREATE_STREAM` record с `source-snapshot` монитора; RMS тот же код, что
   в wasapi-петле). Нет Pulse → тот же вежливый JSON.
3. Автозапуск Linux: в `desktop/main.js` развилка `process.platform === 'linux'`
   — писать/удалять `~/.config/autostart/friend.desktop` (Exec=path к
   билду, X-GNOME-Autostart-enabled).
4. `start.sh`: `go build` → бинарь `companion` без `.exe`, запуск electron;
   `chmod +x`.
5. Проверка: самопроверка под `xvfb-run` (CI), фокус-тест — запускаем
   `xterm`, ждём в потоке его имя; звук — тест схемы (Pulse на CI нет →
   заглушка с причиной ok).

### Этап 8б. macOS

1. `server/cmd/focuswatch/collect_darwin.go`: pure Go через `dlopen`
   (libobjc send/alloc + NSWorkspace, CGWindowListCopyWindowInfo,
   CGEventSourceSecondsSinceLastEventType); без cgo. Активное приложение
   — без разрешений; границы окон — с Accessibility-разрешением (нет —
   `bounds: null`, страница живёт без «на окне»).
2. `server/cmd/soundwatch/level_darwin.go`: возвращает честную причину
   «нет системного loopback». Танец на Mac: feed её голоса (работает) +
   опция «слышать колонки через микрофон» (страница считает RMS из
   getUserMedia — тот же приватный контур, что wake word).
3. Автозапуск трей — родные Electron-механизмы; `NSMicrophoneUsageDescription`
   в build-конфиге.
4. `start.command` (+ chmod) и `electron-builder` dmg (arm64+x64).
5. Проверка: `go build`+`go test` в CI на macos-latest; полная самопроверка —
   руками на живом Маке (на CI у macOS нет window server, GUI-тесты не гоняем).

### Этап 8в. Упаковка и CI (общее)

1. `electron-builder`: Windows NSIS, macOS dmg, Linux AppImage+deb; Go-бинарь
   (companion, focuswatch, soundwatch) внутри пакета (`extraResources`),
   сборка Go под нужную ОСь в prebuild-шаге.
2. GitHub Actions матрица `windows / ubuntu / macos`: `go vet`, `go test`,
   сборка всех трёх бинарей на каждой ОСи (GOOS cross-compile) + `npm build`;
   Linux-часть самопроверки — `xvfb-run npx electron . --selftest`.
3. README: раздел «Запуск на своей системе» (win/linux/mac) + таблица
   границ фич (из этого раздела, человеческим языком).
4. Аудит путей: греп фиксированных `\` в Go-строках и `%AppData%` вне
   UserConfigDir (страница localStorage — ок, сервер — конфиг-дири).

### Риски и ограничения (чтобы не обещать лишнего)

- Wayland: слежение за окнами невозможно из песочницы — фича «понимание
  окна» и «посадка на окне» на Wayland не работает (X11-сессии — работают).
- macOS: танец под чужую музыку без стороннего виртуального аудиодрайвера
  невозможен — остаётся её голос и опциональный микрофон.
- Linux без композитора: прозрачность окна — на совести окружения.
- Linux-трей: без `libappindicator` трей не ставим (EPA: окно остаётся,
  «скрыть» сворачивается в невидимость как сейчас).
- faster-whisper/edge-tts на mac/linux: ставит человек (`pip install`),
  модель 75 МБ качается один раз при первом включении.

### Порядок сдачи

8а (Linux) → 8б (macOS) → 8в (упаковка+CI). Каждый подэтап: `go test`
зелёный, живая самопроверка на соответствующей ОСи, вывод в README.
Windows-часть (24 части) при этом не должна деградировать ни на одну строку.
